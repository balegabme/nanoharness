# Improvements

Flaw and improvement ledger (plan §4 rule 5). The `log_improvement` tool
appends entries under dated headings; the harness-editor ticks one off with a
ref once it is fixed.

In this repo the ledger is this file. In any other workspace it is
`.nanoharness/improvements.md`, because the installed package directory is
never written to.

A ticked entry moves to `docs/improvements-archive.md`, so this file lists
only what is still open.

## 2026-09-04

- [ ] The provider has no request timeout and no retry: a hung connection hangs the session with no way out except quitting the app. Needs a stall deadline on the SSE reader plus backoff on 429 and 5xx (src/providers/openai.ts).
- [ ] There are no tests, and `vitest --passWithNoTests` keeps CI green anyway, so the badge on a public README currently proves only that the code compiles. Plan §16 names the strategy: recorded fixtures for the SSE and schema translation layers, smoke tests against a mock provider.
- [ ] Running out of `maxToolRounds` emits `session.finished` like a normal completion. The last round's tool results are never sent back to the model and nothing tells the user the turn was cut short (src/core/session.ts).
- [ ] `parseWire` assigns `JSON.parse` straight into a typed variable, so a malformed provider payload is trusted and never rejected (src/providers/openai.ts). (partly fixed 2026-09-13: the usage object goes through `parseUsage`, which rejects a report missing its totals or contradicting itself; the delta shapes are still trusted.)
- [ ] An unknown tool name returns a result without `isError` or `content`, unlike every other error path in the loop (src/core/session.ts).
- [ ] `usage.jsonl` grows without bound. It needs rotation or a size cap before long-running installs accumulate years of turns (src/core/usage-log.ts).
- [ ] The preload ships as an ES module, which forces `sandbox: false` on the window. Building it as CommonJS instead would let the sandbox go back on; context isolation covers the bridge either way (src/main/window.ts).
- [ ] Main and renderer share one tsconfig, so `lib` carries DOM types into main-process code that has no business using them. Split the two once the renderer grows (tsconfig.json).
- [ ] The `read` tool's `offset` is a zero-based line index and the tool description does not say so, so a model that thinks in line numbers reads one line off (src/tools/read.ts).
- [ ] The key is encrypted with Electron `safeStorage`, not the OS credential store plan §11 asks for (Windows Credential Manager / Keychain / libsecret). safeStorage is DPAPI-backed on Windows and good enough to ship, but a key encrypted under one OS user cannot be read by another, and the failure is silent, since setup just asks again (src/main/config-store.ts).
- [ ] A settings write that retires the live sessions leaves the transcript on screen showing the old session's turns with no marker that history restarted (src/renderer/index.ts).
- [ ] `harnessEditorCwd()` exists and is tested by hand, but nothing calls it yet: the harness-editor agent itself is build step 3 (src/core/roots.ts).
- [ ] The model picker has no capability warnings. Plan §11 wants per-model checks (no vision, no tool use, no effort levels) from Anthropic `capabilities` or a one-token probe on OpenAI-compatible servers (src/renderer/index.ts). (partly fixed: effort levels and prices are read from the `/models` answer where it carries them (src/providers/model-facts.ts), and a model it describes neither for is marked in settings and can be filled in by hand. Nothing probes, and vision and tool use are still unchecked.)
- [ ] Switching the active model means opening settings and saving. The header chip shows the model but is not a picker, even though the allowlist is right there (src/renderer/index.ts).
- [ ] There is no electron-builder configuration yet, so the brand mark is the window icon but not the installer or executable icon (package.json).
- [ ] `Menu.setApplicationMenu(null)` also removes the accelerators that came with the default menu. Text editing is handled by Chromium so copy and paste still work, but a deliberate keyboard map (plan §13) has to register its own shortcuts (src/main/window.ts).
- [ ] With the environment variables gone, a machine whose OS has no secret store (Linux without libsecret) cannot save a key at all, so the app is unusable there. It needs a real fallback instead of a refusal: an OS-agnostic encrypted store, or an explicit, clearly labelled plaintext opt-in (src/main/config-store.ts).
- [ ] Nothing can configure a provider without the GUI, so headless runs and CI have no way in. A `nh config` subcommand writing the same files is the missing half (src/cli/index.ts, src/main/config-store.ts).
- [ ] The model picker has no capability warnings, and the Anthropic side could read them straight from `GET /v1/models` without probing (src/providers/anthropic.ts, src/renderer/index.ts). (partly fixed: both wires read effort levels and prices out of their `/models` answer, and Anthropic's `capabilities` block is read for the levels and for the output ceiling (src/providers/model-facts.ts). It carries no prices, so an Anthropic model stays marked for those until the user types them in. Vision and tool use are unchecked, and nothing probes.)
- [ ] Nothing sends `cache_control` on the Anthropic wire, so prompt caching never engages and `cacheWrite` stays zero on that provider (src/providers/anthropic.ts).
- [ ] Effort is one global setting. Plan §11 wants it per agent, alongside a per-agent provider and model (src/core/config.ts).

## 2026-09-05

- [ ] Permission grants live in memory on the broker and nothing shows them. A session can be holding several outside paths with no list of what it may reach and no way to take one back short of restarting the app (src/main/permission.ts).
- [ ] `workspace:add` opens a native directory picker, which no headless run can drive, so the one path into the whole workspace feature is exercised by hand only. It needs a seam, with the chosen directory passed in, so a probe can add a folder the way the user does (src/main/index.ts).
- [ ] A permission request that arrives for a session other than the one on screen is auto-denied. That is the safe answer, but a background turn loses its work with nothing to tell the user why (src/renderer/index.ts).
- [ ] Reasoning text from an OpenAI-compatible server is streamed to the screen and then dropped. Nothing on that wire signs it or requires it back, so there is no correctness bug, but a replayed session still shows no thinking on that side (src/core/session.ts, src/main/workspace-store.ts).
- [ ] Stop aborts the HTTP request, but a `bash` child process that is already running keeps running to completion; the loop only stops afterwards. The tool needs the session's abort signal wired to the child so a stop kills what it started (src/tools/bash.ts, src/core/session.ts).
- [ ] The alerts toggle is stored in `localStorage`, so it is per renderer origin and not part of the configuration, and nothing syncs it with the OS notification permission if that is refused (src/renderer/notify.ts).
- [ ] `writeGuard` screens the planner's shell by pattern, so a command that builds its target at runtime, or writes through a program the patterns do not name, gets through. It is a screen for an agent that is not trying to escape, and no kind of boundary; the sandbox in plan §16 is the real answer (src/tools/bash.ts).
- [ ] A background clone gets no `job_update` tool, because adding one would change the tool definitions and invalidate the cached prefix the mode exists to reuse. So a cloned job is silent until it finishes, and the strip shows it as running with nothing to say (src/main/index.ts, src/core/spawn.ts).
- [ ] Jobs live in memory and cannot be stopped. A job that is still running when the app quits dies with the process and leaves whatever it wrote half-done, and there is no button to end one that has gone wrong (src/core/jobs.ts, src/renderer/jobs.ts).
- [ ] Switching a session's role retires the live session, so the next message rebuilds it from the transcript. The transcript keeps the old role's tool calls, and nothing on screen marks where the role changed (src/main/index.ts, src/renderer/index.ts).

## 2026-09-06

- [ ] A failed MCP server is reported only to the main process's console, which is discarded on Windows. `McpHub.status` holds the reason and nothing surfaces it, so a session has no search tool and never says why (src/mcp/hub.ts, src/main/index.ts, src/renderer/index.ts).
- [ ] MCP servers are configured by hand-editing `.nanoharness/mcp.json`. There is no settings screen for them, so adding a server means knowing the file exists (src/renderer/settings.ts).
- [ ] OAuth 2.1 + PKCE is unimplemented for HTTP servers. A 401 with `WWW-Authenticate: Bearer resource_metadata=…` is reported as a failed connection and never starts the flow plan §7 describes, so a server that does not take a static bearer token cannot be reached at all (src/mcp/transport.ts).
- [ ] A dropped Streamable HTTP session is detected (404 on a known `Mcp-Session-Id`) and reported, but not re-initialized. The spec's answer is a fresh handshake; this client makes the user restart the session instead (src/mcp/transport.ts).
- [ ] MCP image and audio content blocks are replaced with a placeholder because a tool result reaches the model as a string. Anthropic takes multi-block `tool_result` content, so a vision-capable session is losing a result it could actually use (src/mcp/client.ts, src/core/session.ts).
- [ ] Every MCP server is connected when a session opens, whether or not the turn needs one. A cold `npx -y` is a package download in front of the user's first message (src/mcp/hub.ts).
- [ ] Skills are read once at session build, so a skill added to the workspace is invisible until the next session. That is deliberate, because the list is inside the cached prefix, but nothing tells the user and the reload is not offered (src/core/skills.ts, src/main/index.ts).
- [ ] Nothing checks that an MCP server's tool count is sane before its definitions go in front of every request. A server publishing eighty tools multiplies the per-request cost of every turn in that session with nothing saying so, and the cost dashboard cannot attribute it (src/mcp/hub.ts).
- [ ] A settings write that retires the live sessions closes their MCP servers too, including one a background job is in the middle of using. The job keeps the tool objects it was built with, so its next MCP call fails on a connection that was closed underneath it (src/main/index.ts, src/core/jobs.ts).
- [ ] Plan §2 names Tavily as the default web search, added when `TAVILY_API_KEY` is set. That default is gone by decision: a harness that arrives with servers the user did not configure spawns subprocesses on their machine on its own authority, and pays for the tool definitions on every request. `examples/mcp.json` is the replacement, and the agent can write it. If the plan is to keep §2 as written, this is the divergence to argue with (docs/harness/mcp.md, src/mcp/config.ts).
- [ ] An MCP server added during a turn is not connected until the session is rebuilt, and nothing rebuilds it. The agent tells the user, but the user's only move is to switch sessions or restart the app. A "reconnect servers" action that retires and rebuilds one session is the missing half (src/main/index.ts, src/renderer/index.ts).
- [ ] Plan §7 asks for a bounded transient retry on an MCP call that fails on the transport and not in the tool. Nothing retries: a single dropped connection is one failed tool call the model has to notice and repeat (src/mcp/hub.ts, src/mcp/client.ts).
- [ ] The failure behind `nh mcp` was not only the missing command: nothing in the prompt would have named it if it had existed. Every subcommand the CLI grows has that problem and the prompt cannot list them all, so an agent needs one cheap way to ask what the harness can do (src/core/agents.ts, src/cli/index.ts).
- [ ] The repeat breaker keys on the tool name and the exact argument string, so a model that varies one character, with a different `offset` or a re-worded grep for the same thing, loops as long as it likes. Catching that needs a similarity measure, and a wrong one would refuse work that was making progress (src/core/session.ts).
- [ ] Notes are stored with the session and never redacted. Whatever a harness note quotes, a path or a command or what a failing tool printed, is written to `sessions/<id>.json` as-is, like the transcript beside it (src/main/workspace-store.ts).
- [ ] `harnessEditorCwd()` exists and nothing calls it, so a harness-editor subagent runs with the summoning workspace as its cwd and under that workspace's access gate. Editing the harness from another project therefore raises a permission prompt for every write, and plan §5's "the harness is its workspace" is not what happens (src/core/roots.ts, src/main/index.ts).
- [ ] A session transcript that will not parse opens as an empty conversation, and the next turn writes the file back, so a corrupt or half-written `sessions/<id>.json` is replaced without a word by a session with no history and what was in it is gone for good. Damage deserves a different answer from absence: the damaged file should be kept aside and the session should say what happened (src/main/workspace-store.ts).
- [ ] The secret store answers "no secrets" when the encrypted blob cannot be decrypted, which is what happens after a machine change or a different OS user. The file is still there, the keys are still in it, and the app shows an empty list, so the user's move is to re-paste keys they did not know they still had. Undecryptable is worth saying out loud (src/main/secret-store.ts).

### Why a turn takes as long as it does

Three findings from one 12-minute research turn. Nothing here is specific to what it was asked; the same three would slow any turn that goes looking through the repo. A subagent answering a question about this one made 80 tool calls over 48 provider rounds, 74 of them shell commands.

- [ ] Every shell command runs on its own. `read` is the only tool that declares itself parallel, so two independent greps in one message run one after the other while two reads do not. In the turn above, 32 of the 33 rounds that asked for two things held a shell command and serialized; the one round that asked for two reads ran them together. `GUARDED_BASH_TOOL` already has `writeGuard` in front of it and cannot write, which is the whole of what `parallel` asks for (src/tools/bash.ts, src/core/session.ts).
- [ ] There is no way to search except by starting a shell, and starting one costs about a second. Every grep, every glob and every look at a range of lines goes through `bash`, and `run()` in src/tools/bash.ts writes the command to a script file, calls `execFile` on Git Bash, captures the output and deletes the script. On this machine `bash -c true` takes 885 ms and a small grep through it takes 1,268 ms, so roughly 70% of a search is the shell starting up and 30% is the search. The turn above ran 74 of them, so about 65 seconds of its 673 went on starting processes, before the serialization above is counted. A tool that searched in-process would pay none of that, and because it could not write it could declare itself parallel, so ten searches in one message would take as long as one (src/tools/bash.ts, src/core/agents.ts).
- [ ] Nothing remembers which files have been read, so the same regions are fetched again across separate round trips. The session tracks files it *wrote*, in `turnFiles`, and keeps nothing equivalent for reads. The bytes are still in the conversation, but nothing indexes them and nothing can answer a repeat cheaply, so the model greps again. In the turn above, `src/renderer/chat.ts` was fetched by 13 separate commands: lines 215 to 275 in one, 265 to 340 in another, then 215 to 248 a third time, each one its own shell and its own round trip. `src/core/session.ts` went the same way through 16 commands. A read index keyed on path and modification time could answer an unchanged repeat with a pointer to the result already in the conversation, which is shorter than the file and costs no process at all (src/core/session.ts, src/tools/read.ts).

## 2026-09-23

- [ ] Plan §15 and step 7 ask for an OCR path: a screenshot that is mostly text costs 700 to 1,500 tokens as a picture and 200 to 400 as the text on it. It is not built. A picture goes to the model as a picture, and a model that does not take images cannot be sent one at all (src/renderer/images.ts, src/core/session.ts).
- [ ] Plan §6 names PowerShell as the shell on a Windows machine without Git for Windows. It is not built, so on such a machine the `bash` tool refuses, every hook is a note and the prompt says there is no shell (src/env/shell.ts).
- [ ] The `bash` tool's timeout kills bash and nothing under it. On Windows a process the script started keeps the pipes open, and the call does not return until that process ends on its own. Hooks stop the whole tree with `taskkill /T` or a process group, and the tool could do the same (src/tools/bash.ts, src/hooks/hooks.ts).
- [ ] A picture's width and height are taken from the window as sent. They only feed the context estimate, and a caller that lied would only skew the meter, but the main process could read both from the image header instead of trusting them (src/main/workspace-store.ts).
- [ ] A send that fails after it has left the composer loses the draft: the text and the pictures are cleared when the message is drawn, before the main process answers. The two refusals the window can foresee, pictures over the limits and a model known not to take them, are caught before that point; a provider that refuses a picture is not (src/renderer/index.ts).
